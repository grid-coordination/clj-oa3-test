## Findings

### 1. `POST /events` returns 400 with self-inflicted validation error  [BLOCKER]

**Severity:** blocks ~45 of the 45 non-passing tests.

**Reproducer:**

```bash
JWT=$(curl -s -X POST -d 'grant_type=client_credentials&client_id=bl_client&scope=test/BL' \
        http://localhost:9090/default/token | jq -r .access_token)

PROGRAM_ID=$(curl -s -X POST -H "Authorization: Bearer $JWT" -H "Content-Type: application/json" \
        -d '{"programName":"DiagProgram"}' \
        http://localhost:8080/openadr3/3.1.0/programs | jq -r .id)

curl -s -X POST -H "Authorization: Bearer $JWT" -H "Content-Type: application/json" -d "{
  \"programID\":\"$PROGRAM_ID\",
  \"eventName\":\"DiagEvent\",
  \"intervalPeriod\":{\"start\":\"2026-05-07T22:00:00Z\"},
  \"intervals\":[{\"id\":0,\"payloads\":[{\"type\":\"PRICE\",\"values\":[1.0]}]}]
}" http://localhost:8080/openadr3/3.1.0/events
```

**Request body sent:**
```json
{
  "programID": "<a valid program UUID>",
  "eventName": "DiagEvent",
  "intervalPeriod": {"start": "2026-05-07T22:00:00Z"},
  "intervals": [{"id": 0, "payloads": [{"type": "PRICE", "values": [1.0]}]}]
}
```

`intervals[0].id` is `0` (integer literal in the JSON), per the OpenADR 3 spec which defines `Interval.id` as `type: integer, format: int32` and a "client generated number".

**Response (HTTP 400):**
```json
{
  "detail": [{
    "type": "int_parsing",
    "loc": ["body", "intervals", 0, "id"],
    "msg": "Input should be a valid integer, unable to parse string as an integer",
    "input": "832d2277-ceec-4102-8ab1-9b0a3b9ec6e1"
  }]
}
```

The VTN reports a validation error at `body.intervals[0].id` and tells us the input it saw was `"832d2277-…"` (a UUID string). That UUID does not appear anywhere in the request body. So somewhere between request parse and field validation the VTN is substituting a UUID into the interval's `id` field — and then rejecting that substituted value because the field is typed `integer`.

Same response with the same UUID-in-`input` shape every time — i.e. it's deterministic per request, not a stale-cache thing. `event.id`, `program.id`, and `ven.id` are all spec-typed as UUIDs (`objectID`); only `interval.id` is integer. My guess is some shared model/validator is conflating those in `oadr_vtn_ri/models/_generated.py` or in an Event/Interval `model_validator`.

**Cascade impact:**

- 15 fail in `events` (every test that needs to create or read an event)
- 14 err in `reports` (the test wants to attach a report to an event, has no event ID, can't form a valid report request)
- 4 fail / 1 err in `mqtt` (event-create / event-update / event-delete / targeted-event / report-* notifications all need an event)
- 1 fail in `ven-client` (test-poll-events)
- 1 fail in `webhook` (event-create webhook)

If this one bug is fixed I'd expect roughly **45 of the 45 failures** to resolve, taking the suite from 151/196 to ~196/196.

### 2. `vens` — `GET /vens/{id}` body has `venName: null`

**Severity:** likely small.

`test-search-ven-by-id-bl` fails on:
```
expected: (= "ven1" (-> resp :body :venName))
actual:   (not (= "ven1" nil))
```

The VEN was registered with `venName: "ven1"` and the search-list test passes; only the by-id case returns `venName: null`. Looks like a serialization or by-id projection bug — worth a quick look in the VENs controller and the `Ven` response model.

### 3. `topics` — VEN-scope cross-access returns 200 instead of 403

**Severity:** depends on the auth model.

`test-mqtt-topics-ven1` and `test-mqtt-topics-ven2` each have 5 sub-assertions checking that `ven1` cannot access `ven2`'s VEN-scoped topics (and vice-versa). All those sub-assertions get HTTP 200 instead of the expected 403.

The mock-oauth2-server JSON_CONFIG sets `sub: ven_client` / `sub: ven_client2` distinctly, but only injects `scope: test/VEN` for both — so the JWTs *do* have a unique `sub` per client. If the VTN derives the principal from the `sub` claim, per-VEN scope enforcement should be possible without changing the mock-oauth2 config. If the VTN only looks at `scope`, both VEN tokens are indistinguishable to it, and this is "by design (with this mock-oauth2 config)" rather than a bug.

It's worth being explicit which of those is intended.

### 4. `webhook` — webhook delivery is unimplemented on this branch

**Severity:** documentation / capability mismatch.

The `/notifiers` endpoint advertises `WEBHOOK: true`, and `notifications.bindings: [WEBHOOK, MQTT]` is honoured at startup. But `oadr_vtn_ri/notifiers.py:64` explicitly filters webhooks out of dispatch:

```python
available_bindings = [b for b in settings.notifications.bindings if b != NotificationBinding.WEBHOOK]
```

So no notification is ever delivered via the webhook binding, regardless of subscription state. That's why both program webhook tests fail to receive a notification (and the third webhook test is a cascade of #1).

The simplest fix is probably to either implement webhook dispatch alongside MQTT in `notifiers.py`, or — until that lands — drop `WEBHOOK` from the `notifications.bindings` default and from the `/notifiers` response so clients don't expect deliveries that never come.

### 5. `mqtt` — NPE on `test-ven-update-notification`

**Severity:** real bug, low-frequency.

```
Cannot invoke "Object.hashCode()" because "key" is null
```

A null key being hashed somewhere in the VEN-update notification path. I haven't traced this back to a controller — happy to share more diagnosis if useful.

### 6. `ven-client` — auto-resolved VEN-scoped topics differ from explicit

`test-ven-scoped-topics-auto-id` fails on:
```
expected: (= (:body auto) (:body explicit))
actual:   (not (= {:id ..., :topics ...} ...))
```

Topics fetched via `GET /notifiers/mqtt/topics/vens/{auto-id}` (where the client resolves its own VEN id from registration) differ from the same call with the id passed explicitly. Looks like a per-call response-id reshuffling, or a small discrepancy in topic shapes between the two paths.

### 7. Dynsec MQTT mode: `/notifiers` advertises an MQTT username that doesn't exist in the broker  [BLOCKER for any dynsec client]

**Severity:** blocks the entire dynsec MQTT flow from a third-party client.

For context: on `main`, the same clj-oa3-test suite runs cleanly in dynsec mode — 195/196, with `mqtt`, `mqtt-auth`, `topics`, `channel`, `ven-client`, and `webhook` all green. The dynsec path is a known-working pattern in this codebase; this finding is about the fastapi branch's `/notifiers` shape diverging from it.

I tried a separate run on fastapi with `mqtt.broker.auth: OAUTH2_BEARER_TOKEN` and `uv run poe bootstrap-mqtt`-generated dynsec config (via a `docker-compose.override.yaml` that mounted `cfg/mosquitto/dynsec/` and switched mosquitto to `-c mosquitto-dynsec.conf`). The broker-side dynsec setup works:

- The VTN authenticates to the broker as `vtn-admin` (per `dynamic-security.json` from bootstrap) and initialises `DynsecManager` cleanly.
- `mosquitto_pub -u vtn-admin -P vtn-admin-password -t test/x -m hello` from the host succeeds.
- The bootstrap script also seeded a `bl_client` account in `dynamic-security.json`.

But `GET /notifiers` (as either BL or VEN, with valid JWTs) returns:

```json
"MQTT": {
  "URIS": ["mqtt://mqtt"],
  "authentication": {
    "method": "OAUTH2_BEARER_TOKEN",
    "username": "oauth2"
  }
}
```

— no `password` field, and **no `oauth2` user in the broker's dynsec ACLs**. So a client following `/notifiers` faithfully picks up an empty/`oauth2`-with-no-password credential pair, attempts to connect, and gets `MqttSecurityException: Not authorized to connect`.

The `docs/mqtt-auth.md` on this branch describes a per-VEN username/password flow (`ven-{venID}` accounts provisioned at REST registration time, returned in `/notifiers` for that VEN). The provisioning side appears wired up — `dynamic-security.json` contained `ven-{UUID}` entries from prior state — but the `/notifiers` response doesn't surface those credentials. Either the username/password flow described in the docs isn't being used to fill the `MQTT.authentication` block, or there's a "Phase 2 / OAuth-bearer-token" path that's only partially implemented.

For the integration suite the practical effect is: dynsec MQTT mode can't be exercised end-to-end on this branch right now. The clj-oa3-test `:mqtt`, `:channel`, `:ven_client`, and `:mqtt-auth` suites all fail to connect to the broker. This wasn't a problem in anonymous-MQTT mode (the run summarized above) because no credentials are needed — the per-suite numbers above stand.

What would unblock this:

1. Have `/notifiers` return the per-VEN dynsec username and password (matching what `docs/mqtt-auth.md` describes).
2. Or, if `OAUTH2_BEARER_TOKEN` mode genuinely intends "client passes its HTTP JWT as the MQTT password" (with the broker validating via OAuth introspection), document that and ensure the broker side is configured for it. Currently the broker is dynsec-only and there's no `oauth2` user.

## Setup notes

**MQTT broker URI advertised in `/notifiers` isn't reachable from outside the Compose network.** The VTN advertises `mqtt://mqtt` (the Compose-internal hostname), which a host-side client can't reach. I worked around it on the test-harness side by adding a `:mqtt-brokers` override in the test config — but it might be worth either:

- A VTN config knob to advertise an externally-reachable broker URI (`MQTT__BROKER__ADVERTISED_HOST`?), parallel to `WEBHOOK__REPLACE_LOCALHOST`, or
- A docs note saying "if you're running clients on the Docker host, override the broker URI"

Outside the compose flow:
- `poe start` (= `fastapi run`) defaults to port 8000 and ignores `config.yaml`'s `server.port`. `python -m oadr_vtn_ri.main` reads it, or `fastapi run --port 8080 oadr_vtn_ri/main.py` works as a host-side override.

**MQTT authentication**: I attempted a dynsec-mode pass on fastapi separately — see finding #7. The broker-side dynsec setup works, but `/notifiers` advertises an MQTT username that doesn't exist in the broker, so no third-party client can complete the connection. The corresponding dynsec flow on `main` was re-run as part of this campaign and passed 195/196 — see *Comparison with `main`*.
