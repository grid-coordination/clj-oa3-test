### 3. `topics` — VEN-scope cross-access returns 200 instead of 403
**PARTIALLY ADDRESSED.** Commit `caa6e96` ("enforce per-VEN scope on MQTT topic endpoints") landed, but the surviving 2 failures in `topics` are not on the per-VEN endpoints I incorrectly framed yesterday — they're on the **global** topic endpoints when called by a VEN. Concretely, `test-mqtt-topics-ven1` and `test-mqtt-topics-ven2` each fail 5 sub-assertions on:

- `GET /notifiers/mqtt/topics/events`
- `GET /notifiers/mqtt/topics/reports`
- `GET /notifiers/mqtt/topics/subscriptions`
- `GET /notifiers/mqtt/topics/vens`
- `GET /notifiers/mqtt/topics/resources`

The test asserts these return **403** when called by a VEN client (since the global topics list is BL-scoped per OA3). Today they return **200**. The per-VEN endpoints (`/topics/vens/{id}`, `/topics/programs/{id}/...`) — which `caa6e96` targets — are now 200/403 correctly.

(My yesterday's prose described this as cross-VEN access, which was wrong — the test code at `topics_test.clj:43-49` only ever calls these endpoints with the client's own VEN id, never the other VEN's. The actual gap is BL-vs-VEN role enforcement on the global topics endpoints.)

### 4. `webhook` — webhook delivery is unimplemented on this branch
**MISDIAGNOSED YESTERDAY; new failure mode today.**

Yesterday's report cited the WEBHOOK filter at `oadr_vtn_ri/notifiers.py:63`:
```python
available_bindings = [b for b in settings.notifications.bindings if b != NotificationBinding.WEBHOOK]
```
That filter is still in place, but it's on the unified `notifiers.py:dispatch_notifications` path — which is **not** what subscription-callback delivery uses. Subscription-bound webhooks are dispatched via `subscriptions_controller.py:subscription_callback()` (line ~70-105), which does call `httpx.AsyncClient.post(callback_url, ...)`. So webhook delivery has been wired all along; yesterday's "no notification is ever delivered" diagnosis was incorrect.

Today's actual failure: the VTN attempts the POST and gets `httpcore.ConnectError: All connection attempts failed`. From `vtn` container logs:

```
ERROR oadr_vtn_ri.controllers.subscriptions_controller: subscription_callback(): webhook POST failed
httpx.ConnectError: All connection attempts failed
```

Root cause: the test harness's webhook receiver binds to `127.0.0.1`, so the registered `callbackUrl` is `http://127.0.0.1:<random-port>/...`. The VTN's `WEBHOOK__REPLACE_LOCALHOST=host.docker.internal` rewrite (`subscriptions_controller.py:84-85`) only matches the literal substring `//localhost:`:

```python
callback_url = callback_url.replace("//localhost:", f"//{settings.webhook.replace_localhost}:", 1)
```

so `//127.0.0.1:` passes through unchanged and the container's loopback can't reach the host process.

What would unblock this:
1. Extend the rewrite to also match `//127.0.0.1:` (one-liner).
2. Or, document the `localhost`-only rewrite contract and we'll switch the harness's webhook receiver to bind on `localhost`.
3. (Optionally also drop the dead `notifiers.py:63` WEBHOOK filter — it's misleading. As of this branch, all webhook dispatch happens through `subscription_callback`, and the filter is never hit by anything that would have actually used a WEBHOOK binding.)

## Setup notes

- The compose stack defaults to `VTN_CONFIG=config.yaml`, which has only `WEBHOOK` in `notifications.bindings`. Use `VTN_CONFIG=config-mqtt.yaml docker compose up -d` to enable the MQTT binding so `/notifiers` advertises MQTT — otherwise the entire `mqtt`, `channel`, `topics`, `ven-client` MQTT path is excluded.
- mock-oauth2-server (3.0.1) requires a `client_secret` parameter on the token endpoint (any value will do). Yesterday's reproducer omitted it — likely an oversight in the curl example, since the actual integration run does send one.
- The VTN advertises `mqtt://mqtt` (Compose-internal hostname) in `/notifiers`, unreachable from the host. The harness's `:mqtt-brokers ["tcp://127.0.0.1:1883"]` override (clj-oa3-test commit `41b350d`) handles this.
